---
name: analisi
description: Analyze a ticket, issue or bug report (Azure DevOps, GitHub, Jira or pasted text) by cross-checking docs/wiki, code, git history and data to find where the problem is and propose the minimal fix. Works in any repo. Use when the user asks to analyze/read a ticket, issue, PBI, work item or bug report, or calls Kowalski by name (e.g. "/kowalski:analisi 15307", "kowalski, analisi del 15307", "analizza il pbi 15307").
argument-hint: <ticket id, issue URL or description>
---

Take the problem described by $ARGUMENTS (if empty, from the user's message; if none, ask). It can be an Azure DevOps work item id, a GitHub issue number or URL, a Jira (or other tracker) key/URL, or pasted text (bug report, customer email, error, stack trace). Use the documentation and find where the problem may be.

0. **Context** (main thread): detect the tracker from `git remote get-url origin` and the shape of the input. Never guess org, project or ids: ask.
   - **Azure DevOps** (`dev.azure.com` / `visualstudio.com`): derive org and project. `https://<org>@dev.azure.com/<org>/<project>/_git/<repo>` or `git@ssh.dev.azure.com:v3/<org>/<project>/<repo>` → `ORG=https://dev.azure.com/<org>`, `PROJECT=<project>`. Wiki: `az devops wiki list --org $ORG --project $PROJECT -o table` → wiki repo URL (usually `https://<org>@dev.azure.com/<org>/<project>/_git/<project>.wiki`).
   - **GitHub**: `gh issue view <n> --comments` (or the URL). Wiki: `<repo>.wiki.git`, if it exists.
   - **Other trackers** (Jira, Linear, ...): use a connector/MCP or CLI if available in the session; otherwise ask the user to paste the text.
   - **Pasted text**: use it as is.
1. **Ticket** (main thread): read it. On Azure DevOps (`ID` = the work item id): `az boards work-item show --id $ID --org $ORG --expand all -o json`; read Title, Description, ReproSteps, AcceptanceCriteria, History, relations (parent/child/PR). Comments: REST `GET $ORG/$PROJECT/_apis/wit/workItems/$ID/comments?api-version=7.1-preview.4`. Download attachments/screenshots if needed (token: `az account get-access-token --resource 499b84ac-1321-427f-aa17-267ca6975798`). List the distinct requests and keywords (features, tables/views/SPs, error messages, codes quoted by the customer). Classify: **bug** (needs the root cause in code) or **operational request / data fix** (often a documented procedure + data check is enough).
2. **Parallel research**: in a single message, launch one subagent per investigation type (Agent tool, `subagent_type: Explore`), passing each the requests and keywords from step 1 and asking for a concise report with precise references, not file dumps. For a data fix with an obvious documented procedure you may skip git and code and verify it yourself.
   - **Docs** (`model: haiku`): sources are whatever exists: tracker wiki, in-repo docs (`docs/`, `wiki/`, README, CLAUDE.md/AGENTS.md, ADRs). Before launching, clone a wiki repo into the scratchpad yourself (Explore agents are read-only; some files fail checkout on Windows, ignore them) and pass the path. Search the keywords, favoring the sections for the current repo's product (Troubleshooting, Procedures, Projects). If the docs say nothing, it must say so explicitly.
   - **Git history and branches** (`model: sonnet`): relevant code may not be on the main branch. `git log --all --oneline -i --grep=<word>`, `git branch -a --contains <commit>`, `git grep <pattern> <branch>`; linked PRs usually explain current behavior. Report relevant commits, PRs, branches.
   - **Code** (`model: sonnet`): for each request find the file and line causing the behavior (`path:line`) and all callers (grep), including SQL scripts/views/SPs in the repo.
3. **Data** (main thread, only if the problem involves data): check the database **read-only** (queries that only read; on SQL Server, e.g. `sys.sql_modules` finds views/SPs using a table). Use connections documented in the repo or in memory; never print passwords. If the docs have a query, run it as is with the ticket's values. Report real numbers (rows found, missing, already fixed), not estimates.
4. **Synthesis** (main thread): cross-check the reports, personally verify the key points cited (read the lines), and propose the minimal fix to the root cause. If a report is vague or conflicts with another, relaunch a targeted subagent instead of redoing the search yourself. Anything not verified must be stated as "not verified".

**Output**: written for a person, not for an agent. In the user's language, concise, plain words: a colleague who hasn't read the code must understand it in one read. No intro, no repetition, no internal jargon (subagents, tool output, raw logs).
- Open with one sentence: what is wrong and why (the root cause), or "not found" and what was ruled out.
- Per request: what happens, where (`path:line`, branch or doc page, as a reference), the minimal fix. Short bullets.
- Add a small diagram (ASCII flow, sequence or table) only when the problem spans several steps, components or branches and a picture is faster to grasp than prose. Otherwise no diagram.
- Close with risks (e.g. branches to align) and open questions (max 3, numbered), only if there are any.
Keep it on one screen; extra details only on request. Do not modify code, write to the DB, or comment on the ticket without confirmation. If asked later to comment: on Azure DevOps use the REST comments API with the HTML text on a single line (`az --discussion` truncates text at the first newline); on GitHub use `gh issue comment`.
